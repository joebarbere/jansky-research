\title{torch-dsp: Coherent Dedispersion, SumThreshold RFI Excision, and a Fast Folding
Algorithm as Pure PyTorch Tensor Operations}
\author[0009-0008-3289-4447]{Joseph Barbere}
\affiliation{Independent researcher}

\begin{abstract}
Coherent dedispersion for pulsar and FRB work lives in compiled codes, none of them
PyTorch or JAX: C++/CUDA
\citep{vanstraten2011,bassa2017}; the SumThreshold and spectral-kurtosis RFI filters
\citep{offringa2010,nita2010} have GPU implementations only behind CUDA-locked CuPy
\citep{kania2026}; and no GPU Fast Folding Algorithm \citep{staelin1969,morello2020}
was publicly usable as of this writing. We present \code{torch-dsp}: all three as pure
PyTorch tensor operations under one \code{device=} argument covering CPU, CUDA, and
ROCm, benchmarked on a consumer AMD RX 7600 XT, a card no production pulsar code
supports.
Correctness is checked per kernel. The chirp matches the cold-plasma dispersion law to
a group-delay residual of $\tdRealGroupDelayResid$ samples (the 99.5\%-energy impulse
round trip bounds precision only), and its sign convention is measured on real data:
the conjugate kernel does not sharpen the burst. Spectral kurtosis and sequential-mode
SumThreshold are byte-identical to tested CPU references; the tensor-parallel
SumThreshold's evaluation-order difference is quantified (Jaccard \tdRealStJaccard,
swept and split by direction). The FFA recovers an injected period to the nearest
drift-grid point against a brute-force folding oracle. Coherent dedispersion of a
CHIME/FRB baseband event \citep{chimebaseband2024} maximises the burst S/N at the
catalogue DM (\tdRealChimeDm\,pc\,cm$^{-3}$) among trials at 0, $\pm$5,
$\pm$20\,pc\,cm$^{-3}$; the tensor SumThreshold mask agrees with the CPU reference at
Jaccard \tdRealCrabJaccard\ on real Parkes RFI. A planned Crab-pulsar validation
returns a calibrated null instead: the \tdRealCrabDur-s file gives fold S/N
\tdRealCrabFoldPub\ at the published period against a same-volume noise level of
\tdRealCrabNoiseSnr, with injected pulses recovered only from \tdRealCrabInjMin$\sigma$
per pulse. Kernel checks re-run on a ROCm device reproduce the CPU results. Benchmarks are single-session
with hardware introspected, not typed: the FFA runs \tdRealSpeedupFfa$\times$ faster
on the GPU (\tdRealBenchFfaCpu\,s to \tdRealBenchFfaGpu\,s); the chirp is
transfer-bound to near parity; the SumThreshold's per-series loop is GPU-hostile. The
implementation favors portability over speed.
\end{abstract}

\section{Introduction}
A device-portable, dependency-light DSP stack matters most to the users production codes
tend to ignore: consumer GPUs (AMD in particular), teaching environments, and small archival
projects. Our earlier \code{torch-fdmt} showed the pattern for incoherent dedispersion,
using the FDMT of \citealt{zackay2017} as gather/roll/add tensor ops. We extend it here to
the coherent-DSP layer. A per-kernel novelty scan (repository-level, 2026-07) found coherent
dedispersion already implemented in C++/CUDA \citep[dspsr, CDMT;][]{vanstraten2011,bassa2017},
in Julia, and in a SYCL prototype, but not in PyTorch or JAX; the claim made here is
therefore pure-PyTorch and pip-installable, not first-portable. GPU SumThreshold and
spectral-kurtosis implementations exist only CuPy-locked \citep{kania2026}. For the FFA,
riptide \citep{morello2020} is CPU-only (its GPU feature request was closed unimplemented in
2024), and a CUDA FFA scaffold appeared on GitHub on 2026-06-12, concurrent CUDA work
\citep{gaffa}; the torch niche remains empty.

\section{Kernels and validation}
\label{sec:kernels}
\subsection{Coherent dedispersion}
The dispersion chirp \citep{hankins1975} is applied per channelized-voltage channel as an
FFT multiply, and inter-channel delays are integer-sample gathers. Two numerical points
matter for the implementation. First, the chirp phase reaches $10^3$--$10^4$\,rad per
0.39-MHz channel at CHIME DMs (band bottom to top) and $>$$10^6$\,rad in wideband use, where
float32 accumulation would genuinely smear the signal; it is therefore accumulated in
float64, wrapped mod $2\pi$, and only then cast to float32, so the FFTs run in complex64
(where consumer GPUs actually perform) at $<$$10^{-6}$\,rad phase error. Second, all
channels are batched into single FFT calls, since a per-channel host loop erases GPU gains,
the same lesson hit and fixed in \code{torch-fdmt}. Two conventions are stated rather than
assumed. The kernel's sign depends on the backend's sideband/conjugation convention (dspsr
parameterises this directly); the round-trip test is sign-self-consistent by construction,
so the sign is anchored by a measurement on the CHIME leg: dedispersing with the
conjugate kernel at the catalogue DM returns S/N \tdRealChimeConjSnr\ where the shipped sign
returns 4.0, and other backends may need the conjugate. Both the chirp multiply and the
inter-channel gather are circular, with no overlap-save discard region, which is correct for
a burst captured mid-buffer but requires overlap-save on top for streaming use. Validation
is two-layered, because a round trip against the exact inverse filter composes the chirp
with its own negation and can never expose a wrong dispersion law. The law itself is checked
directly: the chirp's numerical group delay matches the cold-plasma
$k_\mathrm{DM}\,\mathrm{DM}\,\nu^{-2}$ delay to $\tdRealGroupDelayResid$ samples across the
channel, a check that fails loudly for a wrong constant or exponent. The round trip then
bounds numerical precision: an impulse dispersed by the exact inverse filter (DM 100--150)
re-collapses to zero peak offset with 99.5\% of its energy re-concentrated (through
\code{dedisperse\_channelized}, the wrapped-complex64 path every science and benchmark
result uses, as well as through the complex128 single-channel variant), while a wrong-DM
control stays smeared.

\subsection{RFI excision}
Spectral kurtosis \citep{nita2010} is a two-moment reduction, byte-identical to the
reference (max difference $\tdRealSkMaxDiffSci$). SumThreshold \citep{offringa2010} is
subtler, because the reference implementation flags windows sequentially within each pass,
earlier flags changing later window means, and no tensor formulation reproduces this
cheaply. We ship both modes. The sequential mode is proven byte-identical to the tested CPU
reference, pinning the kernel maths (thresholds, robust noise floors, mask threading). The
tensor-parallel mode evaluates all windows of a pass from the pass-start mask via cumulative
sums; its agreement with the reference is quantified rather than asserted, and because the
divergence is generated by flags taking effect mid-pass, it is bounded across the settings
that grow it, not quoted at the friendliest one: over thresholds 3.0--4.0 and one or two
outer iterations the committed sweep spans Jaccard \tdRealStJaccardLo--\tdRealStJaccardHi\
on synthetic RFI
(\tdRealStJaccard\ at the shipped default, degrading with flag occupancy and iteration
count as the mechanism predicts), and \tdRealCrabJaccard\ on real Parkes data. The
symmetric difference is also split by direction, since over-flagging (data loss) and
under-flagging (missed RFI) are operationally different: at the default the two modes'
exclusive flags are nearly balanced on synthetic RFI (\tdRealStParOnly\ parallel-only vs
\tdRealStCpuOnly\ reference-only samples), while on the Parkes data the parallel mode
over-flags (\tdRealCrabParOnly\ vs \tdRealCrabCpuOnly\ of $\sim$524k samples: data loss,
not missed RFI). Injected narrowband and broadband RFI are fully caught by both modes. Note that
\code{torch}'s even-length median takes the lower middle element where NumPy averages, so
robust-statistics scalars must be computed NumPy-side, or the masks silently diverge.

\subsection{Fast folding algorithm}
The implementation follows the radix-2 Staelin recursion, with each merge stage expressed
as a batched gather over per-drift circular shifts (periods $p + j/(m{-}1)$ samples).
Against a brute-force folding oracle sharing the same profile S/N statistic, an injected
233.7-sample period is recovered to the nearest drift-grid point (the injected value is
not on the grid, whose spacing here is \tdRealFfaDriftRes\ samples, so the rounded error
\tdRealFfaErr\ means ``within one grid cell,'' not ``exactly'') at S/N \tdRealFfaSnr\
(oracle: \tdRealOracleSnr\ at the exact period). The S/N gap is quantitatively predicted and
checked against the measurement: power-of-two row truncation ($\sqrt{2^{\lfloor\log_2 m\rfloor}/m}$)
times $\sim$2-bin quantisation smearing ($1/\sqrt2$) predicts a ratio of
\tdRealFfaRatioPred, against a measured \tdRealFfaRatioMeas; both are committed. On flat
noise the FFA's best peak stays at the noise level.

\section{Real data}
The science legs below were run on CPU; the timings in Section~\ref{sec:bench} were measured
on a ROCm device (RX 7600 XT), a card absent from every production pulsar pipeline's support
matrix. Cross-device agreement is measured rather than assumed: the full offline kernel
suite (chirp round trips, spectral-kurtosis and SumThreshold oracle comparisons, and the
FFA recover-a-known) was re-run on the ROCm device in the same session as the benchmarks
and committed alongside the CPU results (\code{cross\_device\_check} in
\code{results/torchdsp\_metrics.json}).

\subsection{CHIME/FRB baseband event}
We coherently dedisperse the tied-beam voltages of FRB\,20181231C
\citep[150\,MB public release;][]{chimebaseband2024,michilli2021}, both polarizations,
\tdRealChimeNchan\ good channels (\tdRealChimeBw\,MHz), and scan trial DMs. The 0.256-ms
boxcar S/N is maximised at the Catalog-2 \citep{cat2} DM of \tdRealChimeDm\,pc\,cm$^{-3}$
(S/N 4.0 there, $\le\tdRealChimeOffMax$ at $\pm$5 and $\pm$20\,pc\,cm$^{-3}$); the DM-0 trial returns 2.4,
reflecting undispersed RFI/noise structure rather than the burst. The boxcar maximum is a
search over the whole series, so the argmax of every trial is committed
(\code{chime\_peak\_sample\_vs\_dm}): the off-catalogue maxima fall at unrelated positions,
consistent with noise excursions in trials whose residual inter-channel smear ($\sim$7\,ms
across the saved band at $\Delta\mathrm{DM}=5$) buries the burst. That smearing figure is
also why the test is more discriminating than the modest S/N suggests: at DM 556 the
intra-channel smear alone is $\sim$3--28\,ms across the band, one to two orders above
the 0.256-ms boxcar, so any boxcar detection at all requires the coherent chirp, and its
sign, to be right; incoherent inter-channel alignment alone would leave the burst smeared
away. The six-point grid localises the DM only to $\pm$5, so the structure is taken as a
validation of the machinery (and of the chirp sign, via the conjugate trial of
Section~\ref{sec:kernels}) rather than as a DM measurement.

\subsection{Parkes Crab filterbank: a calibrated null}
The tensor SumThreshold mask agrees with the CPU reference at Jaccard \tdRealCrabJaccard\ on
real RFI. The planned Crab period re-find, however, is not supported by this
\tdRealCrabDur-s file, and the null now carries its own calibration rather than an
attribution. The brute fold at the published 33.7\,ms gives S/N \tdRealCrabFoldPub\ (nothing
to find; the file was vendored for giant-pulse work). The FFA's formal peak
(\tdRealCrabPeriodMs\,ms, S/N 5.2) sits at the measured noise level for this search volume
(the same length and period range on pure noise returns \tdRealCrabNoiseSnr) and is
reported as not significant. What the file could have seen is measured by injection: a pulse
train at the published period added to the real dedispersed series is recovered only from
\tdRealCrabInjMin$\sigma$ per pulse (committed as a ladder), so the data length, not the
algorithm, is the limit, now shown directly rather than assumed. The synthetic injections carry
the FFA's validation.

\section{Benchmarks and limits}
\label{sec:bench}
Both timing columns come from one invocation in one session: the GPU and CPU legs run
back-to-back in the same interpreter and the same virtual environment, after a GPU warm-up
call, with the hardware strings for both produced by \code{torch}/platform introspection
rather than typed (GPU: \tdBenchHwGpu; CPU: \tdBenchHwCpu; benchmark shapes and numbers in
\code{results/torchdsp\_metrics.json}). The FFA gains \tdRealSpeedupFfa$\times$ on the GPU
(\tdRealBenchFfaCpu\,s to \tdRealBenchFfaGpu\,s for $2^{22}$ samples $\times$ 64 base
periods), because its gather merges vectorise fully. The chirp (64 channels $\times$ $10^6$
samples) runs at \tdRealBenchChirpGpu\,s on the GPU versus \tdRealBenchChirpCpu\,s on CPU.
Host-to-device transfer of half a gigabyte of voltages is part of the measured time, and the
transfer/compute split has not been profiled; device-resident streaming is expected to
change the balance, but this is stated as an expectation, not a measurement. The current
SumThreshold is GPU-hostile (\tdRealBenchStCpu\,s on CPU versus \tdRealBenchStGpu\,s on
GPU), because its outer loop over series is host-side, the same vectorization wall
documented for \code{torch-fdmt}. A batched 2-D variant is the stated next step, not an
implied capability. No comparison is made against tuned CUDA codes on datacentre GPUs; the
contribution is a single pip-installable, autograd-native implementation that runs from one
code path on CPU, CUDA and ROCm, including hardware nothing else supports, with the
cross-device agreement of every kernel check committed (Section 3) rather than assumed.

Every number above is generated by \code{jansky\_research.torchdsp}
(\code{results/torchdsp\_metrics.json} $\to$ macros). The real-data legs use CANFAR DOI
10.11570/23.0029 (public, no auth) and the sigpyproc3 test filterbank; the kernel checks and
benchmarks are computed on synthetic arrays generated in process.
